A ledger keyed only by `decision_id` can silently reuse a prior denial with different reasons; a composite `(adapter_id, decision_id)` key and exact immutable field comparison make retries idempotent *and* conflicts explicit. **New refinement — receipt/request binding (R6k candidate, NOT TESTED).** Even a field-bound ledger can be unsafe if its lookup layer returns a valid-looking receipt for the *wrong* request key. The caller must compare `requested(adapter_id, decision_id)` to the **receipt's own embedded** `adapter_id, decision_id` and bind `projection_digest, identity_version, lifecycle_version, verdict, reason` to that receipt. The ledger's response should be authenticated and immutable outside the mutable adapter; otherwise a forged matching JSON document is only self-attestation. On mismatch or unavailable durable confirmation: `DENIED_UNRECORDED` (or a distinct `RECEIPT_KEY_MISMATCH` denial), never `DENIED_RECORDED`. A retry of an identical request returns the original receipt; conflicting fields under the same key produce `DECISION_ID_CONFLICT` with no mutation. The witness holder, signing/attestation mechanism, retention and atomic append semantics remain for Timothy/contract design.
