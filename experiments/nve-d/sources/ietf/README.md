## Candidate NVE-D integration (not promoted)
- **Test node**: an isolated record of an opaque source expression, candidate transformation, run ID, generation budget, seed, and evidence references. The source expression must not be parsed into presumed operators.
- **Snapshot**: immutable pre-run expression and experiment setup; record content digest.
- **Template**: optional proposed configuration generator, explicitly marked a hypothesis rather than a semantic truth.
- **Chrono-Tool analogue**: finite, reproducible generation budgets and checkpoint/resume; rotate 250, 1000, 2500, 5000, 10000+ actual completed generations as feasible. No claim of simulated time dilation or infinite parallelism.
- **Nested meta-domain analogue**: bounded parent/child experimental runs with explicit ancestry; recursion depth and generation count are separate experimental variables.
- **Aggregation**: append-only historical evidence; retain conflicting interpretations and `0` outcomes.
- **Evaluation**: only `{<,>,=,0}` as evaluation labels and `∆` for relational change; comparisons must state candidate criterion, evidence and reference. No forced ordering.
- **DFE**: Step 5 evaluation, Step 7 meta-audit, Step 8 revision must revisit previously documented evaluations, including assumptions of the evaluator and auditor.
- **Isolation**: no automatic Registry 0 promotion, deployment, merge, or modification of protected code.

## Falsifiable first tests
1. Verify raw expression preservation through snapshot, branching and checkpoint/resume, including unusual punctuation and nested kernel forms.
2. Compare independent nodes with shared and conflicting hypotheses; detect accidental cross-node mutation.
3. Test that resumed runs reproduce uninterrupted runs with equal seeds and finite budgets.
4. Vary generation count independently from nesting depth; measure actual completed work.
5. Inject unsupported audit assumptions; ensure they are recorded as challenges rather than accepted conclusions.
6. Preserve disagreements between multiple auditors and revisions across hourly runs.

These are proposals and must not be described as completed tests. The IETF codices are historical architectural proposals, not executable code or validated capabilities.
